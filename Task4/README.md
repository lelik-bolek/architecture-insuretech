# Задание 4. Проектирование сервиса продажи ОСАГО

## 1. Архитектура сервиса osago-aggregator и хранилище данных

### Хранилище данных для osago-aggregator
* **Первоначальная мысль:** Сделать сервис полностью stateless в оперативной памяти либо использовать реляционную базу данных (PostgreSQL), как в других сервисах системы.
* **Итоговое решение:** Использовать быстрое in-memory хранилище данных **Redis (`osago-redis`)** с поддержкой времени жизни записей (TTL)[.
* **Почему так:** 
  1. *Работа в распределенной среде (Multi-instance):* По условию сервисы развернуты в нескольких репликах под управлением HPA. Если опрос 10 страховых компаний (до 60 секунд) начнется на одном поде, а этот под упадет или перезагрузится, то при сохранении статусов в локальной памяти контекст будет безвозвратно потерян. Общий Redis позволяет любой соседней реплике подхватить опрос.
  2. *Временный характер данных:* Котировки живут всего несколько минут. В PostgreSQL пришлось бы постоянно запускать тяжелые операции очистки (`DELETE` / `VACUUM`). В Redis ключи сессий очищаются автоматически по истечении таймера (`TTL = 60s`), что защищает память от переполнения.

### Контракт API osago-aggregator для core-app
* **Первоначальная мысль:** Сделать синхронный REST/gRPC метод, где `core-app` делает запрос и держит соединение 60 секунд.
* **Итоговое решение:** Асинхронное событийно-ориентированное взаимодействие (EDA). 
* **Контракт взаимодействия:**
  * Сервис слушает события на создание расчета из топика **`osago.requests.v1`**.
  * По мере получения ответов от страховых компаний сервис публикует события с готовыми котировками в топик **`osago.quotes.v1`**.

## 2. Средство интеграции core-app и osago-aggregator

* **Первоначальная мысль:** Использовать REST API или gRPC с блокировкой потока.
* **Итоговое решение:** Асинхронный обмен через шину событий **Apache Kafka**.
* **Почему так:** Если 2 500 пользователей одновременно отправят заявки, синхронный вызов заблокирует 2 500 потоков веб-сервера на 60 секунд. Это приведет к исчерпанию пула потоков (Thread Pool Exhaustion) и каскадному падению бэкенда. Брокер сообщений Kafka буферизует пиковую нагрузку и развязывает сервисы по времени.

## 3. Интеграция «Веб-приложение (SPA) ↔ core-app» и клиентский API

### Средство интеграции (Front-to-Back)
* **Первоначальная мысль:** Использовать периодический опрос (Long Polling).
* **Итоговое решение:** Использовать однонаправленный потоковый протокол **Server-Sent Events (SSE)** (на схеме отражен отдельной стрелкой).
* **Почему так:** 
  * Требование бизнеса — показывать предложение от каждой СК сразу, как только поступил ответ (до 60 секунд). 
  * В случае Long Polling после ответа первой же страховой компании соединение разрывается. Чтобы получить оставшиеся 9 предложений, браузеру придется заново переоткрывать HTTP-соединения, делать сетевые рукопожатия и слать заголовки. Для 2 500 пользователей это создаст десятки тысяч повторных запросов. 
  * SSE держит **ровно одно легкое HTTP-соединение** и передает котировки потоком по мере их появления на бэкенде.

### API веб-приложения в core-app
1. `POST /api/v1/osago/applications` — синхронный первичный REST-запрос на создание заявки (клиент передает данные автомобиля и водителя, получает уникальный `application_id`).
2. `GET /api/v1/osago/quotes/stream?app_id={id}` — открытие стримингового канала связи по протоколу SSE (`Content-Type: text/event-stream`) для получения котировок в режиме реального времени.

## 4. Паттерны отказоустойчивости (отображение на схеме)

Для защиты сервисов от перегрузок и изоляции сбоев применены 4 паттерна, на схеме показаны элементами из библиотеки:

1. **Rate Limiting (`prIcon=job`):**
   * *На входе в систему (API Gateway / Ingress):* Защищает наш сервис от лавинообразных всплесков трафика свыше запланированных 2 500 одновременных пользователей.
   * *На выходе к API страховых компаний:* Защищает внешние партнерские API от перегрузки. Если 2 500 пользователей нажмут «Рассчитать», мы не должны выдать 2 500 RPS на каждую СК, а обязаны ограничить поток в рамках согласованного лимита по договору.
2. **Circuit Breaker (`prIcon=c_role`):**
   * *На исходящих клиентах к API СК:* Если одна из 10 компаний «лежит» или отвечает сплошными ошибками 5xx, предохранитель временно размыкает цепь к этой конкретной СК. Мы не ждем бессмысленно 60 секунд, сохраняем сетевые ресурсы и отдаем пользователю предложения от остальных 9 работающих компаний.
3. **TimeOut (`prIcon=quota`):**
   * *Внешний тайм-аут:* Жесткий лимит общего ожидания предложений от СК в **60 секунд** по требованию бизнеса. По истечении этого времени опрос прекращается, а сессия закрывается.
   * *Сетевой тайм-аут:* Короткие таймауты (2–3 секунды) на одиночные HTTP-запросы к API СК, чтобы зависшие вызовы не блокировали потоки воркеров.
4. **Retry (`prIcon=deploy`):**
   * *На создании заявки в СК:* Применяется с экспоненциальной задержкой (Backoff) только для первичного вызова `POST /applications` при кратковременных сетевых сбоях (ошибки 502/503/504). Повторять сам опрос статуса бессмысленно, так как он и так выполняется циклически.
