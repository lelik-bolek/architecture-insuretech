# Задание 5. Проектирование GraphQL API для сервиса client-info

## 1. Анализ проблем исходного REST API

Исходный Swagger-контракт сервиса `client-info` предоставлял 3 независимых ресурса:
* `GET /clients/{id}` — базовая информация о клиенте (`id`, `name`, `age`).
* `GET /clients/{id}/documents` — перечень документов клиента.
* `GET /clients/{id}/relatives` — перечень родственников клиента.

При атрибутивном составе карточки клиента до 500 полей такая структура приводила к системным архитектурным проблемам:
1. **Недостаточная выборка (Underfetching):** Для типового бизнес-сценария (например, оформление полиса ОСАГО или страхования жизни) сервису `core-app` и фронтенду требуются имя клиента, данные паспорта и контакты родственников. В REST приходилось выполнять **3 последовательных HTTP-запроса**, что утраивало нагрузку на сервис и создавало пиковый RPS.
2. **Избыточная выборка (Overfetching):** Если экрану требовалось отобразить только ФИО и серию/номер одного документа, сервис в REST был вынужден отдавать полные объекты документов со всеми техническими и сервисными атрибутами.

---

## 2. Архитектурное решение: переход на GraphQL

Разработанная схема GraphQL объединяет разрозненные REST-ресурсы в единый **граф объектов**:
* Корневой объект `Client` включает в себя прямые связи на списки связанных сущностей: `documents: [Document!]` и `relatives: [Relative!]`.
* Все операции чтения агрегированы в единую точку входа — тип **`Query`**, доступный через единственный сетевой эндпоинт `POST /graphql`.

### Соответствие типов данных (Swagger -> GraphQL)
* Идентификаторы `id` переведены из `type: string` в строгий скаляр **`ID!`**, однозначно определяющий первичный ключ сущности.
* Числовые поля (`age`) типизированы как **`Int`**.
* Текстовые поля (`name`, `type`, `relationType`, а также даты `issueDate`, `expiryDate` в формате ISO-8601) описаны базовым типом **`String`**.
* Связанные коллекции описаны как строгие списки без пустых элементов внутри (`[Document!]`, `[Relative!]`).

## 3. Примеры клиентских запросов для различных сценариев

### Сценарий 1. Оформление полиса (комбинированная выборка)
Клиент запрашивает имя, номер документа и родственные связи в рамках **одного сетевого вызова** вместо трёх:

```graphql
query GetClientForInsurance {
  client(id: "usr-4521") {
    name
    documents {
      type
      number
    }
    relatives {
      relationType
      name
    }
  }
}

```

### Сценарий 2. Отображение краткого профиля (защита от Overfetching)

Фронтенд запрашивает только базовые демографические поля, не нагружая БД выборкой тяжелых массивов документов:

```graphql
query GetClientBrief {
  client(id: "usr-4521") {
    name
    age
  }
}

```

## 4. Эффект для архитектуры InsureTech

* **Снижение RPS на сервис client-info:** Потребители объединяют множественные запросы данных карточки клиента в один сетевой вызов.
* **Минимизация сетевого трафика (Bandwidth):** Клиенты получают только те поля из 500 возможных, которые непосредственно отображаются на текущем шаге пользовательского интерфейса.
* **Гибкость развития клиентов:** Добавление новых экранов и витрин не требует доработки бэкенда и создания новых REST-эндпоинтов.
