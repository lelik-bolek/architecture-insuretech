# Анализ архитектуры InsureTech: переход на Event-Driven архитектуру

## 1. Анализ текущего состояния (As-Is) и выявленные проблемы

В текущей реализации обмен данными о доступных страховых продуктах и оформленных полисах построен на синхронных HTTP/REST-вызовах и периодическом пакетном опросе:
1. **Синхронная агрегация при запросе продуктов:** При вызове `GET /products` сервис `ins-product-aggregator` синхронно обращается к пяти внешним страховым компаниям (СК), дожидается всех ответов, объединяет их и возвращает результат вызывающей стороне (`core-app` или `ins-comp-settlement`).
2. **Периодический опрос:**
   * Сервис `core-app` опрашивает `ins-product-aggregator` каждые 15 минут для актуализации локальной витрины продуктов.
   * Сервис `ins-comp-settlement` запрашивает продукты раз в сутки ночью.
3. **Пакетная ночная выгрузка полисов:** Сервис `ins-comp-settlement` раз в сутки обращается в `core-app` по REST API за всем массивом страховок, оформленных за прошедший день.

### Текущие сбои:
* Периодические отказы и таймауты при ответе `ins-product-aggregator`.
* Задержки в API даже одной страховой компании приводят к зависанию или сбою всего агрегированного ответа.
* Ночные пиковые нагрузки на `core-app` при пакетной выгрузке дневных полисов.

## 2. Анализ рисков при планируемом росте (подключение еще 5 СК)

С увеличением числа партнеров-СК с 5 до 10 текущая архитектура станет критическим узким местом:

### Риск 1. Проблема «самого медленного звена» (Cascading Latency)
Время синхронного ответа `ins-product-aggregator` определяется самым медленным API из всех интегрированных СК:
T_response = MAX(T_СК_1, T_СК_2, ..., T_СК_10) + T_overhead
При 10 внешних интеграциях вероятность того, что хотя бы у одной компании возникнет задержка или сетевой лаг, возрастает более чем в два раза. Клиентские запросы будут упираться в таймауты соединений (HTTP 504 Gateway Timeout).

### Риск 2. Падение доступности всей системы (Availability Degradation)
При синхронной каскадной модели общая доступность агрегатора равна произведению доступностей всех внешних систем:
A_aggregator = A_СК_1 * A_СК_2 * ... * A_СК_10
Если каждая СК имеет SLA 99%, итоговая доступность сервиса агрегации упадет до:
0.99 ^ 10 = 0.904 (примерно 90.4%)
Это делает невозможным выполнение бизнес-требования доступности **99,9%**.

### Риск 3. Неэффективное использование ресурсов (Resource Exhaustion)
* При периодическом опросе `core-app` раз в 15 минут большинство запросов являются паразитными, так как продукты и тарифы СК меняются нечасто.
* Опрос 10 СК раз в 15 минут создает постоянную холостую нагрузку на сеть, пулы потоков (thread pool) и сокеты соединений.

### Риск 4. Деградация БД при ночных пакетных запросах (Batch DB Spike)
Запрос сервисом `ins-comp-settlement` суточного реестра полисов через REST API `core-app` приводит к выполнению тяжелого SQL-запроса на большой выборке данных. Под растущей пользовательской нагрузкой это создает резкий дефицит IOPS и блокировки в базе данных `core-db`, создавая риск отказа дневного процессинга оформления.

## 3. Архитектурное решение To-Be: переход на Event-Streaming

Для устранения синхронной связанности и рисков каскадных сбоев внедряется брокер сообщений **Apache Kafka** и организуется шина событий.

### 3.1. Перевод взаимодействия на Event-Streaming

1. **Репликация продуктового каталога (`ins-product-aggregator` -> `core-app`, `ins-comp-settlement`):**
   * `ins-product-aggregator` перестает опрашивать СК «на лету» в момент вызова REST.
   * Сервис агрегации по регламенту раз в 24 часа (по расписанию через cron или по вебхукам от СК) забирает изменения тарифов, нормализует их и сохраняет в собственную БД `aggregator-db`.
   * Изменения публикуются в топик Kafka: **`insurance.products.v1`** (формат Event-Carried State Transfer).
   * `core-app` и `ins-comp-settlement` подписываются на этот топик в рамках независимых Consumer Group и обновляют свои локальные витрины тарифов в режиме реального времени.

2. **Передача оформленных полисов** (core-app -> core-db -> Debezium -> Kafka -> ins-comp-settlement)

   * Шаг 1. **Локальная транзакция (`Transactional Outbox` в `core-app`)**:
   Клиент оформляет и оплачивает страховку. Сервис core-app открывает одну локальную ACID-транзакцию в СУБД `core-db`, куда одновременно сохраняет:
     а) Бизнес-сущность полиса в таблицу policies.
     б) Событие InsurancePolicyIssued в таблицу outbox_events (в формате JSON).
   Это гарантирует: событие зафиксировано строго тогда и только тогда, 
   когда полис сохранен в базе данных (исключена Dual-Write Problem).

   * Шаг 2. **Захват изменений (`Debezium CDC Connector`)**:
   В систему вводится новый инфраструктурный компонент — `Debezium CDC Connector` (на базе Kafka Connect). Debezium непрерывно читает журнал опережающей записи (WAL) базы данных core-db. Как только в таблице outbox_events появляется новая строка, Debezium без нагрузки на ядро БД вычитывает ее и транслирует в топик Kafka `nsurance.policy.events.v1`.

   * Шаг 3. **Асинхронное потребление (`ins-comp-settlement`)**:
   Сервис ins-comp-settlement подписан на топик `insurance.policy.events.v1`. 
   Он вычитывает события по мере их публикации в течение дня и сохраняет в свою базу `settlement-db` с контролем идемпотентности по policy_id. 
   К ночи реестр уже сформирован. Полностью отменяются тяжелый ночной 
   REST-запрос и пиковая нагрузка на core-db.

## 4. Обоснование применения паттерна Transactional Outbox

### Проблема двойной записи (Dual-Write Problem)
Если сервис `core-app` сначала зафиксирует полис в PostgreSQL (`core-db`), а затем попытается отправить событие в Kafka по сети, возникает риск рассинхронизации:
* Если Kafka недоступна или произошел сетевой сбой, полис сохранен, но событие не отправлено -> `ins-comp-settlement` не узнает о страховке, взаиморасчеты с СК нарушатся.
* Если сначала отправить сообщение в брокер, а транзакция в БД упадет по ошибке (Constraint Violation, откат транзакции), во внешнюю систему уйдет фантомное событие о полисе, которого нет в базе данных.

### Решение
В сервисе `core-app` **обязательно применяется паттерн Transactional Outbox**:
1. В рамках **единой локальной ACID-транзакции** в СУБД `core-db` сохраняются:
   * Бизнес-сущность полиса (таблица `policies`).
   * Событие для шины (таблица `outbox_events`).
2. Для публикации событий из таблицы в Kafka применяется механизм **Transaction Log Tailing (Change Data Capture, CDC)** на базе **Debezium**:
   * Debezium отслеживает журнал транзакций PostgreSQL (WAL).
   * Изменения из таблицы `outbox_events` мгновенно транслируются в топик Kafka `insurance.policy.events.v1`.
3. Потребители (`ins-comp-settlement`) реализуют идемпотентную обработку событий (по уникальному `event_id` / `policy_id`), нивелируя дубли при доставке с семантикой At-Least-Once.
